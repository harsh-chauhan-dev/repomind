# RepoMind database design

This document describes the implemented PostgreSQL foundation. The SQL
migrations in [`../database/migrations`](../database/migrations) are the source
of truth; this document explains the relationships and the reasons behind the
constraints and indexes.

## Platform and conventions

- PostgreSQL is provisioned with `pgcrypto` and `pgvector` by
  `001_extensions.sql`.
- Internal records use UUID primary keys generated by `gen_random_uuid()`.
- Timestamps use `timestamptz` and default to `now()`.
- Repository revisions are immutable snapshots identified by a full 40-character
  commit SHA.
- `document_chunks.embedding` is `vector(1536)`. The dimension is a deliberate
  foundation default and must be changed through a migration if the selected
  embedding model changes.
- Statuses are text values protected by `CHECK` constraints so state additions
  can be made with ordinary forward migrations.
- Tokens are stored only as encrypted byte data; encryption keys do not belong
  in PostgreSQL.

## Relationship model

```text
users
 ├── github_accounts
 ├── sessions
 └── repositories
      └── repository_revisions
           ├── indexing_jobs
           └── repository_files
                └── document_chunks

users ── conversations ── messages ── message_sources ── document_chunks
users ── patch_proposals ── repository_revisions
```

### Identity and repository ownership

`users` is the application tenant boundary. Email uniqueness is
case-insensitive through `users_email_lower_unique`. Optional provider identity
fields are paired and unique. Passwords are stored as scrypt password hashes,
never plaintext.

`sessions` stores only SHA-256 hashes of opaque session tokens and CSRF tokens.
Session cookies are HttpOnly; the separate CSRF cookie is intentionally
readable by the client for the double-submit defense. Expired and revoked
sessions are excluded from authentication lookups and are cascade-deleted with
their user.

`github_accounts` belongs to one user and has unique GitHub user IDs. A
repository references both its owner and its GitHub account through a composite
foreign key, preventing a user from attaching another user's account.

`repositories` uses `(owner_user_id, github_repo_id)` as its connection
identity. The same public GitHub repository may therefore be connected by
different RepoMind users without sharing ownership records.

### Revisions and activation

`repository_revisions` is unique per repository and commit SHA. Files, chunks,
jobs, conversations, and proposals refer to a revision rather than mutable
repository state.

`repositories.active_revision_id` is a composite foreign key to
`(repository_revisions.id, repository_revisions.repository_id)`. This prevents
activating a revision belonging to another repository. The foreign key is
deferrable so a transaction can insert a new revision and activate it together.

### Files, chunks, and retrieval

`repository_files` is unique by revision and normalized relative path. The
path check rejects empty, absolute, and traversal paths. `document_chunks`
stores line ranges, source content, content hashes, optional model metadata,
and a pgvector embedding.

The chunk-to-file relationship includes `revision_id` as a composite foreign
key. This makes it impossible for a chunk to claim a file from another
revision. A generated `tsvector` provides lexical search, while the partial
HNSW index supports cosine similarity search for populated embeddings.

### Conversations and citations

Conversations are owned by the repository owner and pinned to one revision.
Their composite foreign keys enforce both ownership and revision/repository
consistency. Messages belong to conversations and message sources connect
assistant evidence to document chunks with cited line ranges.

The application layer must additionally validate that a cited chunk belongs to
the conversation's pinned revision before returning a response. The schema
keeps the chunk and message relationships explicit so this validation has
stable identifiers and indexed joins.

### Indexing jobs

Jobs belong to a revision and have an explicit lifecycle. A partial unique
index permits historical terminal jobs while allowing at most one queued,
running, or retrying job for a revision. Completion timestamps are constrained
to terminal states.

### Patch proposals

`patch_proposals` stores the request, structured plan JSON, optional patch text,
review status, owner, repository, and immutable base revision. The composite
foreign keys prevent proposals from crossing users, repositories, or revisions.
`accepted` means accepted as a RepoMind proposal; it does not apply or push
changes to GitHub.

## Delete behavior

Source-derived rows are revision-owned and cascade from repository deletion:
revisions cascade to jobs and files, files cascade to chunks, and chunks
cascade to message sources. Conversations and proposals cascade from their
owning user/repository. Application services must first stop or invalidate
in-flight jobs before deleting a repository so workers cannot recreate data.

## Migrations and development data

`database/migrate.mjs` applies files matching `NNN_name.sql` in lexical order
and records them in `schema_migrations`. It is idempotent and must be used for
all schema changes.

`database/seeds/001_development.sql` contains deterministic, non-secret data
for local development. It includes a repository, ready revision, source file,
zero-vector chunk, conversation, citation, and draft proposal. It is not a
production fixture.

## Verification

The integration runner recreates the public schema, applies every migration,
checks extensions, tables, vector storage, retrieval indexes, and verifies a
duplicate revision is rejected:

```bash
pnpm db:test
```
